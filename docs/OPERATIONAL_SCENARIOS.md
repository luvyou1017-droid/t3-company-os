# 운영 시나리오 테스트

## 목적

개발 환경에서 지급 운영 흐름을 역할별로 끝까지 재현하고, 상태 전이와 데이터 격리를 자동 검증한다. 계산식이나 실제 운영 저장소를 변경하는 테스트가 아니라 별도의 Mock 시나리오 실행기다.

## 실행 조건과 데이터 분리

- Vite 개발 모드에서만 사이드바의 `운영 시나리오 테스트` 메뉴가 노출된다.
- 기본 데이터 모드가 `local`일 때만 실행된다.
- Supabase 모드에서는 시나리오 데이터 생성과 실행을 차단한다.
- 모든 시나리오 데이터에는 `metadata.isTestData = true`와 `metadata.scenarioId`가 포함된다.
- 데이터는 전용 키 `t3_company_os_dev_operational_scenarios`에만 저장한다.
- 초기화는 선택한 `scenarioId` 데이터만 제거하며 실제 Campaign, Settlement, Payment, Evidence, Withholding 데이터는 삭제하지 않는다.

## 역할별 테스트 순서

정상적인 지급 흐름은 김병희 매니저가 본인 Campaign을 확인하고 증빙을 제출하는 것으로 시작한다. 허수정 정산 담당자가 증빙을 검수하고 지급요청을 생성하며, 허윤정 대표가 승인한다. 마지막 지급 완료 처리는 허수정 정산 담당자가 수행한다.

각 단계 카드에는 현재 사용자, 역할, 실행 가능한 버튼을 표시한다. 시나리오 전용 실행 함수도 역할과 소유권을 검사하므로 UI 숨김만으로 권한을 표현하지 않는다.

## Scenario A · 정상 지급

1. 김병희 매니저 본인 Campaign 조회
2. 매니저 증빙 업로드 및 검수 요청
3. 허수정 My Work 생성
4. 허수정 증빙 승인 및 My Work 완료
5. 허수정 지급요청 생성
6. 허윤정 대표 승인
7. 허수정 지급 완료
8. Timeline, 지급 가능 체크리스트, Activity Log와 중복 방지 검증

## Scenario B · 증빙 반려

1. Revision 1 업로드
2. 허수정 반려 및 사유 저장
3. 업로드자 재업로드 Work Item 생성
4. Revision 2 업로드
5. Revision 1과 `previousEvidenceId` 유지
6. Revision 2 승인
7. 지급요청, 대표 승인, 지급 완료

## Scenario C · 프리랜서 원천세

검증 값은 부가세 포함 정산금 533,120원이다.

- 기준금액: `Math.round(533,120 / 1.1) = 484,655원`
- 소득세: `truncateToTenWon(484,655 × 3%) = 14,530원`
- 지방소득세: `truncateToTenWon(484,655 × 0.3%) = 1,450원`
- 총 원천세: `15,980원`
- 최종 지급액: `468,675원`

기존 `calculateWithholding`을 그대로 호출하며, 동일 지급 건의 원천세 항목이 한 건만 존재하는지 검증한다.

## Scenario D · 권한 차단

- 타인 Campaign의 지급요청에 접근하는 매니저
- 대표 승인을 시도하는 정산 담당자
- 지급 완료를 시도하는 대표
- 지정 검수자 허수정이 아닌 정산 담당자의 증빙 최종 검수 시도

메뉴와 버튼 노출 조건, URL 접근 결과, 소유권 범위와 실행 함수의 저장 차단을 함께 확인한다. 차단 결과는 `403 · 이 작업을 실행할 권한이 없습니다.`로 기록한다.

## Scenario E · 셀러와 매니저 지급 분리

같은 Campaign에서 다음 값이 소유자별로 독립적인지 검증한다.

- evidenceId와 검수 상태
- paymentRequestId와 지급금액
- 대표 승인과 지급 완료 상태
- ownerType이 기록된 Activity Log

한쪽 상태 변경 후 다른 쪽 값이 바뀌면 실패다.

## 성공 기준

- 각 시나리오의 최종 단계가 완료된다.
- 최종 단계의 모든 assertion이 통과한다.
- 원천세와 지급요청이 중복 생성되지 않는다.
- 권한 없는 접근과 저장 호출이 모두 차단된다.
- 셀러와 매니저의 상태 및 이력이 독립적이다.

## 실패 시 확인 항목

- 실패가 표시된 단계 ID
- 예상값과 실제값
- 현재 사용자와 역할
- 이전 단계 실행 여부
- 데이터 모드가 local인지 여부
- Revision 연결 및 ownerType/ownerId
- 지급요청과 원천세의 중복 키

## 실제 운영 데이터와 분리 원칙

운영 저장 키, localStorage fallback, Supabase Provider와 실제 테이블은 시나리오 실행기가 쓰거나 삭제하지 않는다. 테스트 데이터 자동 마이그레이션과 Supabase 삽입도 수행하지 않는다.
